Yesterday, I learned how Git repositories and branches help organize development. Today, I learned how developers propose changes, review code, and collaborate using GitHub Pull Requests.

🔎 𝗧𝗵𝗲 𝗯𝗮𝘀𝗶𝗰 𝗺𝗲𝗻𝘁𝗮𝗹 𝗺𝗼𝗱𝗲𝗹

A Pull Request (PR) is a proposal to merge changes from one branch into another.

It gives team members an opportunity to review changes before they are merged.

𝗖𝗿𝗲𝗮𝘁𝗲 𝗯𝗿𝗮𝗻𝗰𝗵 → 𝗠𝗮𝗸𝗲 𝗰𝗵𝗮𝗻𝗴𝗲𝘀 → 𝗣𝘂𝘀𝗵 → 𝗢𝗽𝗲𝗻 𝗣𝗥 → 𝗥𝗲𝘃𝗶𝗲𝘄 → 𝗠𝗲𝗿𝗴𝗲

A Pull Request is more than a merge button.

It creates a place to discuss code, identify problems, and improve quality before changes reach the target branch.

💻 𝗨𝘀𝗲𝗳𝘂𝗹 𝗚𝗶𝘁 𝗰𝗼𝗺𝗺𝗮𝗻𝗱𝘀

git switch -c feature/update-readme

Creates and switches to a new branch.

git status

Shows the current state of the repository.

git add README.md

Stages the changes.

git commit -m "Update project README"

Records the staged changes.

git push -u origin feature/update-readme

Pushes the feature branch to the remote repository.

After pushing, I can open GitHub and create a Pull Request from the feature branch into the main branch.

git diff main...feature/update-readme

Shows the changes introduced by the feature branch relative to main.

🛡️ 𝗪𝗵𝘆 𝗱𝗼𝗲𝘀 𝘁𝗵𝗶𝘀 𝗺𝗮𝘁𝘁𝗲𝗿 𝗳𝗼𝗿 𝗗𝗲𝘃𝗦𝗲𝗰𝗢𝗽𝘀?

In DevSecOps, code changes can affect applications, infrastructure, deployment pipelines, and security configurations.

Pull Requests help teams:

🔹 Review code before merging
🔹 Identify bugs and insecure configurations
🔹 Discuss improvements with teammates
🔹 Run automated tests and security checks
🔹 Maintain a clear history of changes
🔹 Reduce the risk of introducing problems into the main branch

GitHub can also run CI/CD checks against proposed changes.

For example, a Pull Request can trigger automated tests, dependency checks, and static application security testing (SAST).

These checks help identify issues before changes are merged.

🧪 𝗧𝗼𝗱𝗮𝘆'𝘀 𝗽𝗿𝗮𝗰𝘁𝗶𝗰𝗲

The goal was not just to learn how to create a Pull Request.

The goal was to understand how teams review changes before accepting them.
